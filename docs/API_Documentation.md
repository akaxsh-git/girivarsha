# API Documentation

Base URL (local dev): `http://localhost:8000`. All routes are prefixed with `/api/v1` except `/` and `/docs` (interactive Swagger UI, auto-generated by FastAPI).

Every endpoint below is real — either it works as described, or it returns a `501` with a machine-readable body naming the phase that will implement it. Nothing returns fabricated data.

## Working now (Phase 12)

### `GET /api/v1/evacuation/route/{village_id}`
Real, computed live. Builds a directed graph per micro-catchment (nodes = villages, edges between consecutive elevation-order villages — the same proxy topology already used for `upstream_rainfall`/lead-time), then runs `networkx.shortest_path` with haversine-distance edge weights from the origin village down to its catchment's real lowest-elevation seeded village (never a fabricated "shelter" location). Returns the ordered list of hops (`from`/`to`, `distance_km`), `total_distance_km`, `estimated_minutes` (distance ÷ `ASSUMED_WALKING_SPEED_KMH = 5.0`, cited to Naismith's Rule), and per-hop `unsafe`/`unsafe_reason` flags — a derived heuristic (either hop endpoint currently at `HIGH`/`CRITICAL` live risk), not real road-hazard data. `404` for an unknown village id; `422` if the village has no catchment to route within. `note` on the response spells out explicitly that this is NOT real road/trail routing. See `backend/app/services/evacuation.py`.

### `GET /api/v1/evacuation/priority`
Real, computed live. A transparent ranking, not a composite score or an evacuation order — sorted by current risk-level severity, then ascending lead-time (less warning first, nulls last), then descending risk score. Every input is already real/derived elsewhere in the app (`GET /risk/*`, Phase 10 lead-time); this endpoint only orders them. Accepts optional `?region_id=` (Phase 11) to scope to one region.

### `GET /api/v1/evacuation/routes`
Real, computed live (user-requested follow-up: "an evacuation route for each village"). Returns a list of the SAME `EvacuationRoute` shape `GET /evacuation/route/{id}` returns — one entry per village that has an assigned micro-catchment (villages without one are skipped, not given a fabricated empty route) — by calling that endpoint's exact same underlying computation for every village, nothing duplicated or re-implemented. Accepts optional `?region_id=` to scope to one region, same convention as `/risk/map`/`/evacuation/priority`. The Authority dashboard's evacuation panel uses this to show every village's route at a glance in a summary table, with the existing per-village hop-by-hop detail view kept below it. See `backend/app/api/routes/evacuation.py`.

### `GET /api/v1/replay/events`
Real, DB-backed. Lists only the historical events that have a real, seeded, cited sub-event timeline (currently Kedarnath 2013 and Reni/Tapovan 2021) — an event without a seeded timeline simply doesn't appear here, rather than appearing with a fabricated one.

### `GET /api/v1/replay/{event_id}`
Real, DB-backed. Returns the event plus its full ordered timeline of real, cited sub-events. Each entry carries `occurred_at` and an honest `time_precision` (`exact_time`, `approximate`, or `date_only`) — the public record for both disasters is genuinely incomplete, and gaps/approximate times are labelled as such rather than smoothed into a fabricated minute-by-minute account. Real IST-sourced clock times (e.g. IMD bulletins, survivor-account timestamps) are converted to the correct UTC instant, not mislabeled; `date_only` entries deliberately stay at UTC-midnight (no real clock time exists to convert) so the displayed calendar date isn't shifted backward. `404` if the event has no seeded timeline. See `scripts/seed_event_timelines.py`.

## Working now (Phase 11)

### `GET /api/v1/regions`
Real, DB-backed. The region registry — every real, named Himalayan valley the system knows about, `active` (real village-level data seeded) or `planned` (real and cited, not yet village-sourced — `village_count`/`catchment_count` honestly `0`). See `docs/Region_Onboarding.md` for what moves a region from `planned` to `active`, and `docs/Data_Sources.md` for citations.

`GET /api/v1/villages`, `GET /api/v1/catchments`, and `GET /api/v1/risk/map` all accept an optional `?region_id=` query parameter (an id from `GET /regions`) that scopes the response to one region's villages/catchments only. Omitting it returns everything across every seeded region, unchanged from pre-Phase-11 behaviour — no existing caller breaks. `GET /api/v1/villages` and `GET /api/v1/catchments` responses now also carry `region_id`/`region_name` per row.

## Working now (Phase 9-10)

### `GET /api/v1/model/explanation/{village_id}`
Real, DB-backed. Ranks the active baseline model's own real components by contribution and narrates them in plain language (`summary`, `ranked_drivers`, `model_explained`, `caveat`). This is a genuine model-agnostic explanation of the model that's actually running (`weighted_baseline`) — explicitly NOT a fabricated SHAP explanation of the undeployed Phase 5 ML layer; `caveat` says so in every response. `404` for an unknown village id. See `backend/app/services/explanation.py`.

`GET /api/v1/risk/map` and `GET /api/v1/risk/{village_id}` now also carry real `lead_time_minutes` (int, or honestly `null` for a catchment-source village with nothing upstream) and `lead_time_note` (the full reasoning) — a Phase 10 prototype: straight-line distance to the nearest upstream village (same elevation-order proxy `upstream_rainfall` already used) ÷ a single, conservative, citably-sourced assumed flow velocity. Not validated hydraulic routing — see `backend/app/services/lead_time.py`.

Both endpoints also carry a real `glacial_lake_distance_km` (float, or `null` if the committed lake inventory file is somehow missing) and `glacial_lake_note` (Phase 12 follow-up, user-requested) — real great-circle distance to the nearest of 4,881 real, satellite-mapped Himalayan glacial lakes (Zhang et al. 2023; see `docs/Data_Sources.md`). This is **advisory context only**, never folded into `risk_score`/`risk_level` — see `backend/app/services/glacial_lake_proximity.py`'s module docstring and `docs/Limitations.md` for why.

Both endpoints also carry `glof_contribution_pct`/`glof_contribution_tier` (`GET /risk/{id}` additionally carries `glof_contribution_note`) — a glacier melt-rate follow-up, user-requested: "incorporate the melting rate of nearby glaciers into the risk score and how probable a flash flood is based on nearby glacial data". `glof_contribution_pct` (0-100, or `null` if the committed glacier dataset is missing) is a heuristic, equal-weighted blend of real glacial-lake proximity and a real nearby glacier's melt rate (WGMS/Dussaillant et al. 2025 mass-balance data; see `docs/Data_Sources.md`) — **advisory context only, and explicitly NOT a calibrated statistical flash-flood probability** (no outcome dataset exists to calibrate one against). `glof_contribution_tier` is `LOW`/`MODERATE`/`HIGH`/`null`. Unlike the lake-proximity field, the underlying melt rate itself IS also folded into `risk_score`/`risk_level` as a genuine 5th weighted component (`glacial_melt_rate`, visible in `GET /risk/{id}`'s `drivers.components`) — see `backend/app/services/glacial_melt_hazard.py`'s module docstring and `docs/Limitations.md` for the full reasoning and caveats.

Both endpoints also carry a real, independent **SCS-CN rainfall-runoff estimate** (user-requested follow-up: "a real SCS-CN rainfall-runoff layer... would be the highest-value next addition") — `scs_cn_runoff_depth_mm` (mm) and `scs_cn_curve_number` on `GET /risk/map`; those plus `scs_cn_amc_class` (`I`/`II`/`III`), `scs_cn_hydrologic_soil_group` (`A`-`D`), `scs_cn_land_cover`, `scs_cn_rainfall_depth_mm`, `scs_cn_runoff_ratio`, and `scs_cn_note` on `GET /risk/{id}`. Computed by the standard USDA-SCS/NRCS TR-55 method from each village's real soil texture (ISRIC SoilGrids) and land cover (ESA WorldCover 10m) plus its current rainfall/soil-moisture reading — **shown alongside, never folded into, `risk_score`/`risk_level`**. All fields are honestly `null` (with an explanatory `scs_cn_note`) for a village whose land cover is snow/ice or open water, or if the committed soil/land-cover dataset is missing. See `backend/app/services/scs_cn_runoff.py`'s module docstring and `docs/Data_Sources.md`/`docs/Limitations.md` for every disclosed simplification.

Rainfall and soil-moisture inputs feeding all `/risk/*` endpoints are simulated by default, or **real** (Open-Meteo, free, no API key) when `GIRIVARSHA_ACTIVE_RAINFALL_PROVIDER` / `GIRIVARSHA_ACTIVE_SOIL_PROVIDER` are set to `real` — see docs/Technical_Notes.md's "Real weather data" section and `backend/app/providers/base.py`. `confidence_pct` reflects whichever mix is actually active.

## Working now (Phase 8)

### `GET /api/v1/sensors`
Real, DB-backed. Every registered sensor node with LIVE-computed `status` (`online`/`stale`/`offline`, recomputed from `now - last_seen_at` on every call — never trusted from a stored column), `last_value`/`last_unit` from its most recent reading, and `last_reading_source`. A provisioned-but-never-reported node is honestly `offline` with `last_value: null`, not a fabricated placeholder. See `docs/IoT_Architecture.md`.

### `GET /api/v1/sensor-readings`
Real, DB-backed. Most recent readings across all sensors (`?limit=` up to 500, default 50).

### `POST /api/v1/sensor-reading`
Real ingestion endpoint — what `iot/mqtt_bridge.py` posts to after receiving an MQTT publish. `404` for an unregistered `external_device_id` (a node must be provisioned via `scripts/seed_iot_nodes.py` first — no silent auto-creation). `422` for an unknown `source` value. `source` is self-declared by the publisher and stored as-is (real firmware would send `"real"`; the current simulator always sends `"simulated"`).

## Working now (Phase 4)

### `GET /api/v1/risk/map`
Real. Computes the Phase 4 transparent baseline risk score for every seeded village right now (not cached — recomputed each call from the current simulated readings), persists each as a `RiskPrediction` row, and syncs alerts from the result. Returns `village_id`, `village_name`, `risk_score` (0-100), `risk_level` (`LOW`/`MODERATE`/`HIGH`/`CRITICAL`, from the configurable thresholds in `GET /version`), `confidence_pct`.

### `GET /api/v1/risk/{village_id}`
Real. Same computation as above for one village, plus the full transparent `drivers` breakdown (every component — now 5: `rainfall_intensity`, `soil_moisture`, `upstream_rainfall`, `historical_susceptibility`, `glacial_melt_rate` — each with name, raw value, unit, data source, normalized value, weight, score contribution), a `confidence_explanation`, `lead_time_minutes`/`lead_time_note` (Phase 10), `glacial_lake_distance_km`/`glacial_lake_note` (Phase 12 follow-up — see above), `glof_contribution_pct`/`glof_contribution_tier`/`glof_contribution_note` (glacier melt-rate follow-up — see above), and the `scs_cn_*` rainfall-runoff fields (SCS-CN follow-up — see above). `404` for an unknown village id. See `backend/app/services/risk_engine.py` for the full documented formula.

### `GET /api/v1/alerts`
Real. Returns currently **open** (unresolved) alerts — YELLOW/ORANGE/RED only; a village with no open alert is implicitly GREEN, which never gets its own row. Alerts are synced whenever `GET /risk/map` or `GET /risk/{id}` runs (there's no background scheduler yet — that's Phase 8+), so call one of those first if this looks stale.

## Working now (What-If Simulator follow-up, user-requested)

### `POST /api/v1/simulate`
Real (problem-statement item 20 — previously the last endpoint on the "not yet implemented" list, closed as a user-requested follow-up after the original 14-phase plan). Body: `{"village_id": int, "rainfall_mm_hr"?: float, "soil_moisture_pct"?: float}` — at least one override is required (`422` otherwise, and for a value outside `[0, 500]`/`[0, 100]`). `404` for an unknown village id. Recomputes the SAME `GET /risk/{id}` formula (`app/services/risk_engine.py`) with the given input(s) substituted in — there is no separate "simulation model." Returns both `baseline_risk_score`/`baseline_risk_level`/`baseline_confidence_pct` (the village's real current assessment) and `simulated_risk_score`/`simulated_risk_level`/`simulated_confidence_pct` (the hypothetical one), plus the full `drivers` breakdown for the simulated run and a `note` explaining that overridden inputs are tagged `SIMULATED` and nothing here is persisted or fed into `/alerts`. Any input NOT overridden keeps using this village's real current data (sensor, if online, else the configured provider) exactly as an un-simulated `GET /risk/{id}` call would.

Also returns `baseline_scs_cn_curve_number`/`baseline_scs_cn_runoff_depth_mm`/`baseline_scs_cn_runoff_ratio`/`baseline_scs_cn_note` and the equivalent `simulated_scs_cn_*` fields (SCS-CN follow-up, user-requested) — unlike the glacial-lake/glacier-melt advisory fields, this comparison DOES respond to the rainfall/soil-moisture overrides above, since the SCS-CN runoff estimate is itself computed from those same (possibly overridden) inputs. No extra wiring was needed for this: the simulated run reuses the already-resolved override-aware rainfall/soil values that also feed the weighted score.

## Working now (Phase 2)

### `GET /api/v1/villages`
Real, DB-backed. Returns all seeded villages across every region, ordered by elevation, each with `lat`/`lon`, `coordinate_precision` (`surveyed` or `approximate`), `region_id`/`region_name`, `source`, and `provenance` (citation). Accepts optional `?region_id=` (Phase 11, see above) to scope to one region. See `docs/Data_Sources.md`.

### `GET /api/v1/villages/{id}`
Real, DB-backed. `404` for an unknown id (not a silent empty response).

### `GET /api/v1/catchments`
Real, DB-backed. Returns micro-catchment topology (name, watershed, river, upstream/downstream links, village count). `has_polygon_geometry` is honestly `false` until Phase 3 GIS work delineates real polygons — never a placeholder shape pretending to be real.

### `GET /api/v1/historical-events`
Real, DB-backed. Every event carries a `source_citation` — currently the real, documented 2013 Kedarnath disaster.

## Working since Phase 1

### `GET /`
Root/welcome. Returns app name, tagline, and the standing disclaimer.

### `GET /api/v1/health`
Liveness check. Example:
```json
{"status": "ok", "app": "Girivarsha", "phase": "Phase 9-10 - explainability + lead-time estimation, real weather providers (opt-in)", "time": "2026-09-04T09:00:00Z"}
```

### `GET /api/v1/version`
Model/build governance (problem-statement item 38). Reports the active, configurable risk thresholds and weights, the baseline model's identity (`active_model` — always `weighted_baseline`, `trained: false`, since it's a formula not a fitted model), and the ML layer's real status (`ml_layer.status: "not_deployed"`, with the reason — see `docs/ML_Methodology.md`). `GET /risk/*` is served entirely by `active_model`; `ml_layer` exists so nothing ever silently claims ML backing it doesn't have.

### `GET /api/v1/demo/rainfall-sample?lat=&lon=`
Phase-1-only smoke test exercising the `DataProvider` adapter pattern end to end with `SimulatedRainfallProvider`. Every response is explicitly tagged `"source": "simulated"`. Will be superseded by real risk/sensor endpoints in Phase 4+ and removed then (tracked in `Future_Work.md`).

## Contract defined, not yet implemented (return `HTTP 501`)

No endpoint currently in this table — `POST /api/v1/simulate` (the last one) was built as a user-requested follow-up; see "Working now (What-If Simulator follow-up, user-requested)" above. Whatever's next from `docs/Future_Work.md` (e.g. device authentication) would land here first, honestly, before being implemented.

A `501` body looks like:
```json
{
  "detail": {
    "endpoint": "GET /villages",
    "status": "not_implemented",
    "planned_phase": "Phase 2-3 (DB + map)",
    "message": "This endpoint's contract is defined but not yet backed by real logic..."
  }
}
```

This lets the frontend team build against the real contract today, and lets the backend team implement against a spec that's already agreed — without either side pretending the data exists yet.
