# Failure/Fallback Testing (Phase 13)

## What this phase is, and one honest gap up front

Problem-statement item 31 reportedly names nine specific failure modes the system should handle explicitly. **The exact source text for item 31 could not be located** — it isn't stored anywhere in this repo, and two separate web searches for it during this project returned nothing publicly indexed (SIH problem statements typically live behind a portal, not in general search results). Rather than invent a plausible-sounding list and present it as the real one, this phase instead derives nine real, concrete failure modes directly from this app's own architecture — specifically the fallback hierarchy already documented in `docs/Architecture.md` ("Sensor-failure / fallback hierarchy, problem-statement item 13") and the actual degrade-paths in the provider, risk-engine, sensor-ingestion, and MQTT-bridge code. If the real item-31 list surfaces later, this phase should be revisited against it directly.

Every mode below is tested for the same property: **the app degrades honestly** — no crash, no fabricated data standing in for a real reading, no silent failure — rather than three worse outcomes: crashing the request (or the whole process), returning a plausible-looking but made-up value, or failing in a way nobody would notice until it mattered.

## The nine modes

All tests live in `tests/backend/test_failure_modes.py`, run as part of the normal `pytest` suite (no special setup beyond the usual seeded Postgres). Four modes already had dedicated tests elsewhere before this phase; that file references them rather than duplicating them.

| # | Failure mode | Where it's tested | Honest behavior verified |
|---|---|---|---|
| 1 | A provisioned sensor node has never reported | `tests/backend/test_sensors.py::test_provisioned_but_never_reported_sensor_is_honestly_offline` | Status is `offline`, `last_value` is `None` — never a fabricated reading. |
| 2 | A sensor's last reading has aged past "online" but not past "offline" | `tests/backend/test_sensors.py::test_stale_reading_reports_stale_not_online` | Status is `stale`, computed live from freshness on every request — never trusted from a stored column that could go silently wrong. |
| 3 | An unregistered device tries to report a reading | `tests/backend/test_sensors.py::test_unregistered_device_gets_a_clear_404_not_a_silent_accept` | Clean `404`, not a silent auto-provision of an unknown device. |
| 4 | A sensor payload declares an unrecognized provenance tag | `tests/backend/test_sensors.py::test_invalid_source_is_rejected_not_silently_stored` | Clean `422`, not silently stored as if it were a valid real/simulated/derived tag. |
| 5 | A sensor payload carries a malformed `observed_at` timestamp | `test_failure_modes.py::test_malformed_observed_at_gets_a_clean_422_not_a_crash` | **A real bug, found and fixed by this phase.** Previously crashed with a bare, unhelpful `500` — `POST /sensor-reading` called `datetime.fromisoformat()` unguarded. Fixed in `app/api/routes/sensors.py` to return a clean `422` naming the bad field, same pattern already used for the invalid-source check right above it. |
| 6 | The active REAL weather provider (Open-Meteo) becomes unreachable mid-request | `test_failure_modes.py::test_risk_computation_survives_a_real_provider_outage` | `compute_risk_for_village` already caught `ProviderUnavailableError` per-component (this existed before Phase 13), but nothing had proven end-to-end that a full risk computation survives it. It does: the assessment still returns, the affected component honestly falls back to the `SIMULATED` tier (which is what pulls `confidence_pct` back down), and nothing is silently relabelled as a real reading it isn't. |
| 7 | The glacial-lake-proximity dataset is missing from disk entirely | `test_failure_modes.py::test_risk_endpoint_survives_missing_glacial_lake_dataset` | The underlying lookup already degraded honestly at the unit level (`tests/backend/test_glacial_lake_proximity.py`). This closes the gap one level up: `GET /risk/{id}` still returns `200` with `glacial_lake_distance_km: null` and an explanatory note, and every other field in the response is unaffected — one optional advisory input failing doesn't take down the whole endpoint. |
| 8 | A client queries risk data for a region with zero seeded villages, or a village id that doesn't exist | `test_failure_modes.py::test_risk_map_for_an_unpopulated_planned_region_returns_an_honest_empty_list`, `test_risk_for_nonexistent_village_id_is_a_clean_404` | `GET /risk/map?region_id=<planned>` returns an honest `[]`, never a fabricated placeholder village. `GET /risk/{bad_id}` returns a clean `404` naming the id, not a crash or an empty-but-200 response that could be mistaken for "zero risk." |
| 9 | The MQTT bridge receives a malformed payload, the backend is unreachable when it tries to forward, or a message arrives on an unexpected topic | `test_failure_modes.py::test_mqtt_bridge_drops_malformed_json_without_crashing`, `test_mqtt_bridge_survives_backend_unreachable`, `test_mqtt_bridge_ignores_messages_on_unexpected_topics` | All three were already handled correctly in `iot/mqtt_bridge.py`'s `on_message` (try/except around JSON parsing, try/except around the forwarding POST, a topic-shape check) — this phase adds the regression tests that had never existed to prove it, exercising the real handler function directly rather than requiring a live broker. |

## What this phase deliberately did NOT do

- **It did not fabricate the original problem-statement item 31 text.** See the honest gap noted at the top — this list is real and defensible, but it is this project's own derivation, not a transcription of a source document nobody here has access to.
- **It did not add a generic global exception handler that swallows all errors into a uniform response.** That would make failures *look* handled without actually testing each one's specific, correct degrade behavior — the whole point of this phase. Each mode above was tested and fixed (mode 5) or verified (the other eight) individually.
- **It did not test infrastructure-level failures that need a live process to meaningfully exercise** — e.g. Postgres dying mid-request, or the MQTT broker itself going down while the bridge is connected (as opposed to failing to connect in the first place, which `iot/mqtt_bridge.py`'s own `try/except` around `client.connect()` already handles and logs clearly). Those are real, worth testing with a proper integration harness (a test that actually stops/starts a real Postgres or mosquitto process), which is future work — see `docs/Future_Work.md`.

## Result

66/66 backend tests passing (was 57/57 before this phase — 9 new), full suite (backend + frontend + GIS + ML) 130/130 passing. One real production bug found and fixed along the way (mode 5).
