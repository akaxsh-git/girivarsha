## Real duplicate-alert race condition, found live on the user's own machine (done)

While verifying the sensor-network and performance fixes above, the user's own Authority dashboard showed Kedarnath listed three separate times in the Active Alerts panel, each its own open ORANGE row, while every other village appeared once — not a hypothetical, an actual screenshot. Root-caused, not guessed at: the frontend renders each alert by its own database `id` (`RiskPanel.tsx`, `key={a.id}`), ruling out a rendering bug — the backend had genuinely persisted 3 separate open `Alert` rows for one village. `backend/app/services/alerts_engine.py::sync_alert_for_village` only ever enforced its own documented "one open alert per village" invariant with an in-app check-then-act (SELECT for an existing open alert, then INSERT if none/different level) — safe within a single serialized request, but with nothing backing it up at the database level. Two genuinely concurrent requests scoring the same village around the same moment — an overlapping dashboard poll, or a page refresh fired while a previous slow `/risk/map` call was still in flight (exactly the conditions the pre-performance-fix ~48s `/risk/map`, see below, made likely) — could both see "no open alert yet" and both insert one.

Fixed with two parts: **migration `36ac87f278e4`** first collapses any duplicate open alerts already sitting in a database (keeping only the most recently issued one per village, resolving the rest) so upgrading isn't blocked by the very rows it fixes, then adds a partial unique index (`CREATE UNIQUE INDEX ... ON alerts (village_id) WHERE resolved_at IS NULL`) that makes "at most one open alert per village" a real, Postgres-enforced guarantee instead of just a docstring's claim. **`sync_alert_for_village`** now wraps its insert in a SAVEPOINT (`db.begin_nested()`) and catches the resulting `IntegrityError` on a genuine race, adopting whichever request's alert actually won instead of letting a 500 escape or leaving two open rows for one village.

3 new backend tests (`tests/backend/test_alerts_race_condition.py`): one proves the raw DB constraint rejects a second concurrent open alert using two real, independent sessions (Postgres's own read-committed MVCC semantics make the interleaving exact and deterministic — no thread-timing games needed); one proves `sync_alert_for_village` itself handles that exact race gracefully via a monkeypatched `db.flush` that deterministically forces the race window open at precisely the right moment (again, no thread-timing flakiness); one is a sanity check that ordinary non-racing operation (open, no-op at unchanged level, escalate, resolve on drop to LOW) is completely unaffected by the new SAVEPOINT/IntegrityError machinery. Full backend suite **108/108 passing**.

Anyone running an existing local database needs to run `alembic upgrade head` (same command as always — see README.md "Database setup") to pick up this migration; a fresh `alembic upgrade head` on a new database applies it automatically as part of the normal chain.

## GET /risk/map performance fix + a real cross-catchment "upstream" bug (user-requested follow-up — done)

- [x] **`GET /risk/map` was measured, on the user's own machine with real weather providers active, taking ~48s end-to-end** (`time curl`, confirmed the response itself was fully correct — this was purely a performance/reliability issue, surfacing in the Authority dashboard as a transient "risk data unreachable" while the slow request was in flight). ## IoT device authentication (user-requested follow-up — done)

- [x] **`POST /sensor-reading` now requires a real per-device API key for every sensor that has one**, closing the gap flagged since Phase 8: previously any request naming a registered `external_device_id` was trusted with zero credential check. `sensors.api_key_hash` (migration `5dbcb12077f4`) stores a SHA-256 hex digest of a random `secrets.token_urlsafe(32)` key generated per-device at provisioning time (`scripts/seed_iot_nodes.py`) or via the new idempotent `scripts/rotate_sensor_api_keys.py`; `app/api/routes/sensors.py::post_sensor_reading` reads the credential from a new `X-Device-Api-Key` header (never the JSON body, so it's never logged alongside reading data) and checks it with `hmac.compare_digest` for constant-time comparison. A missing or wrong key on a sensor that has one gets a clean `401`, distinctly logged by `iot/mqtt_bridge.py`.
- [x] **Nullable by design, not by oversight — an honestly staged rollout, never a retroactive lockout.** `api_key_hash` is nullable because real sensor rows already existed in past sessions' seeded databases with no recoverable plaintext key; a `NULL` sensor keeps working exactly as it did before this feature, un-authenticated, until rotated. `GET /sensors`'s new `authenticated` field reports this live per node.
- [x] **End-to-end plumbing, not just the backend check.** `iot/simulate_sensor_publisher.py` reads each device's key from the new gitignored `iot/device_keys.json` (this build's stand-in for a real fleet's own hardware-provisioning pipeline) and includes it in its MQTT payload's `"api_key"` field; `iot/mqtt_bridge.py` forwards it verbatim as the HTTP header, never inspecting or storing it; both real firmware sketches (`iot/firmware/*/*.ino`) gained a `DEVICE_API_KEY` constant with an explicit honesty note that a real deployment must flash this per-board, never hardcode it in shared source, plus a JSON buffer size bump (128→256 bytes) to fit the new field.
- [x] New backend tests (`tests/backend/test_sensors.py`) cover: a reading rejected `401` with no key when the sensor has one, rejected `401` with the wrong key, accepted `201` with the correct key, and the `authenticated` field's correctness on `GET /sensors` — using a dedicated new test device, not the existing `TEST_DEVICE_ID`/`STALE_DEVICE_ID` fixtures, so every previously-passing test is unchanged. A new failure-mode test (`test_failure_modes.py`) proves a wrong-key request degrades honestly (`401`, no side effects on `last_seen_at`/`status`), consistent with every other mode in that file. See `docs/IoT_Architecture.md`'s rewritten "Sensor authentication" section for the full design writeup and `docs/Limitations.md` for what this does and doesn't cover (in particular: no MQTT-broker-level auth, no TLS on either hop).

## Real-regional-data fallback for offline sensors (user-requested follow-up — done)

- [x] **`GET /sensors` now falls back to a REAL Open-Meteo regional weather estimate whenever a sensor has no live/fresh reading of its own** — closing the gap the user raised directly ("why do we need the simulator if we have real values"): before this, an offline sensor showed nothing at all, even though the app already has a real weather data path (the risk engine's `RealRainfallProvider`/`RealSoilMoistureProvider`) that just wasn't connected to the sensor panel. New `SensorOut.fallback_value`/`fallback_unit`/`fallback_source` fields, always `fallback_source: "derived"` when populated, never conflated with `last_value` (that device's own real/simulated reading) or with `status` (which stays an honest fact about the device itself).
- [x] **Only rainfall/soil_moisture sensors get one** — Open-Meteo has no water-level or tilt product, so those two sensor types stay `fallback_value: null`, disclosed in `docs/Limitations.md` rather than guessed around.
- [x] **A real N-sequential-real-HTTP-calls performance bug was found and fixed during this same follow-up, before it ever reached the user**: an early version fetched one real Open-Meteo call per offline sensor, sequentially, inside `GET /sensors`'s per-sensor loop — the exact anti-pattern already found and fixed once for `GET /risk/map` (`prefetch_readings`, ~48s regression, see the entry above). Caught live in this sandbox when a full `test_sensors.py` run hung past 90 seconds. Fixed with the same technique: `_prefetch_regional_fallbacks` collects every UNIQUE (sensor type, ~110m-rounded coordinate) job actually needed for one response and fetches them all concurrently (`ThreadPoolExecutor`) before the per-sensor loop runs, on top of an hourly `@lru_cache` shared across requests.
- [x] **A second, test-suite-only issue found and fixed alongside it**: this sandbox's network to `api.open-meteo.com` is blocked (already disclosed for the existing real providers), so any test anywhere in the suite that hits `GET /sensors` with an offline sensor would otherwise pay a real ~8s connection-timeout tax per unique village/type. Added `tests/backend/conftest.py` — a global autouse fixture making `httpx.get` fail fast by default for every backend test, overridable per-test via the existing `monkeypatch.setattr` pattern already used in `test_providers.py`. This changes no real behavior; it only makes the sandbox's pre-existing network restriction fail fast instead of slow.
- [x] Frontend: `Sensor`'s `fallback_value`/`fallback_unit`/`fallback_source` fields, and `SensorPanel.tsx`'s value cell shows `~{value} {unit} (regional est.)` in a distinct italic/muted style (`.sensor-value-fallback`) with a title tooltip explaining it's not that device's own reading, instead of a bare dash — but only ever instead of `last_value`, never alongside it.
- [x] 5 new backend tests in `tests/backend/test_sensors.py` (offline sensor gets a mocked real fallback; an online sensor never even triggers the fetch; Open-Meteo failure degrades to `null`, not a 500; water_level sensor never gets one; a village-less sensor never gets one) and 2 new frontend tests in `SensorPanel.test.tsx`. Full backend suite **198/198 passing** (was 193/193), full frontend suite **74/74 passing** (was 72/72). `tsc --noEmit`/`npm run build` clean.
