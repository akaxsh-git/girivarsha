# Demo Guide (Phase 14)

**Status: real, rehearsed run instructions** — this replaces the Phase 1 placeholder that said the demo couldn't be rehearsed yet. It now can, and was: every step below was actually executed against a running backend + frontend + IoT stack in this build environment (backend health, all dashboard panels, both regions, the sensor network, evacuation/priority/replay, and the explanation panel) while writing this guide. `docs/Product_Positioning.md` still holds the positioning and stakeholder Q&A; this file is the operational script.

## One honest correction up front (updated since Phase 14, both gaps below now closed)

The original 12-scene script (`docs/Product_Positioning.md`) was written at Phase 1, before the risk engine or IoT pipeline existed, and it assumed two things that, at Phase 14, turned out **not** to match what had been built yet. Both have since been closed as user-requested follow-ups — this section is kept (rather than deleted) so the history is honest about what was missing and when it was fixed:

1. **The What-If Simulator now exists.** `POST /simulate` was an honest `501` stub through Phase 14; it is now real (see "Optional: reliably showing an ORANGE/RED moment" below and the Authority dashboard's "What-if simulator" panel) — a presenter can type in a rainfall/soil-moisture value and watch the SAME transparent baseline formula respond live, no threshold trick needed anymore (though that trick, described further down, still works and is kept documented for reference).
2. **The sensor network is now wired into the risk engine** (`app/services/risk_engine.py` checks each village for a fresh online sensor reading before falling back to the configured provider — see `docs/IoT_Architecture.md`'s "Wired into the risk engine" section). One caveat remains, and it's worth stating plainly to a reviewer rather than letting them assume otherwise: this build's demo sensors still self-report `source: "simulated"` (per Phase 8's honest labelling), so using a sensor instead of a provider does **not** by itself raise `confidence_pct` here — only a real (`source: "real"`) sensor reading would. Sensor status genuinely does flip to `stale`/`offline` when a node stops reporting, and the engine genuinely does fall back correctly when that happens — that part is real and demoable (see Scene 10 below).

Neither gap was hidden before — both were already written down in `docs/Limitations.md`/`docs/Future_Work.md` at the time. What matters for a live demo is that the script matches current reality rather than leaving a presenter to discover a mismatch live in front of an audience — this file is kept current for exactly that reason.

## One-time setup (rehearse this before the actual demo)

Follow `README.md`'s "Running it locally" section in full — Postgres + migrations + all seed scripts (`seed_pilot_region.py`, `seed_chamoli_valley.py`, `seed_regions.py`, `seed_event_timelines.py`, `seed_iot_nodes.py`), backend (`uvicorn`), frontend (`npm run dev`, port 5173 — CORS only allows 5173/3000, see `backend/app/core/config.py`), and the IoT stack (mosquitto + `iot/mqtt_bridge.py` + `iot/simulate_sensor_publisher.py`). Confirm before you start presenting:

- `curl http://localhost:8000/api/v1/version` returns `200` and `build_phase` says the phase you expect.
- The frontend header shows "Backend online" (not "unreachable").
- `curl http://localhost:8000/api/v1/sensors` shows sensors flipping to `online` a few seconds after the simulator starts (12 nodes across both valleys as of this phase).
- The map panel will show a blank/gray tile area if the presenting machine has no route to `tile.openstreetmap.org` — this build environment's own sandbox network is blocked from it (same restriction documented for the DEM/Open-Meteo calls elsewhere), so **test this on the actual presenting machine ahead of time**; a normal internet connection should render it fine.

### Reliably showing an ORANGE/RED moment

**Preferred: the What-If Simulator.** Scroll the Authority dashboard to "What-if simulator", pick a village, enable the rainfall and/or soil-saturation override sliders, drag them up, and click "Run what-if scenario". This calls the real `POST /simulate` (`backend/app/api/routes/risk.py`), which recomputes the SAME baseline formula shown in the risk panel above with your override(s) substituted in — the response shows both the village's real current assessment and the hypothetical one side by side, so the jump from (say) MODERATE to CRITICAL is visible and honestly labelled as hypothetical the whole time (the panel's `note` text says so verbatim). Nothing about this is persisted or fed into `/alerts` — running it twice in a row does not create a fake alert. This is the cleanest way to guarantee an ORANGE/RED moment on demand without touching any configuration.

**Fallback (still works, kept for reference): tightening the risk thresholds.** By default, `SimulatedRainfallProvider`/`SimulatedSoilMoistureProvider` generate modest random values every request (rainfall around a 4mm/hr base, soil moisture around 45%) — real randomness, not a script, which means most villages' un-simulated current state sits LOW/MODERATE most of the time (verified empirically while writing this guide: 6 refreshes of `/risk/map` never exceeded MODERATE with default thresholds). Before the What-If Simulator existed, the honest workaround was to lean on the fact that **the risk thresholds are genuinely configurable, exactly as `docs/Product_Positioning.md`'s stakeholder Q&A already claims** (`GIRIVARSHA_RISK_THRESHOLDS__LOW_MAX`/`..._MODERATE_MAX`/`..._HIGH_MAX` in `backend/.env`). Tightening them before a demo run (e.g. `LOW_MAX=8`, `MODERATE_MAX=16`, `HIGH_MAX=24`) makes the same real, unmodified simulated inputs land in HIGH/CRITICAL far more often — this was verified directly against the real risk engine while writing this guide, and still works today. **Revert `backend/.env` to the defaults after the demo** so the repo's own tests (`tests/backend/test_risk.py` asserts confidence stays honestly capped, not thresholds) aren't affected.

## The scenes (target: under 5 minutes)

**1. Normal state (30s).** Open `/authority`. Point at "Pilot overview": 2 sourced regions, 10 villages monitored, sensors online count, avg lead time. Switch the region selector between "All regions", "Mandakini Valley", and "Chamoli Disaster Valley" to show real per-region scoping (map, village list, sensor count, and the elevation-order line all update — this is `?region_id=` on the real `/villages`/`/catchments`/`/risk/map`/`/sensors`/`/alerts` calls, not a frontend-only filter of fake data).

**2. Risk table + real inputs (30s).** Scroll to "Current risk (baseline)". Point out every village has a live score, level, and confidence — and that confidence is honestly capped (~40% by default) because rainfall/soil are simulated-tier by default. Click a risk row's "component detail" link if you want to show the raw `rainfall_intensity`/`soil_moisture`/`upstream_rainfall`/`historical_susceptibility`/`glacial_melt_rate` breakdown behind the score — this is the real, transparent formula from `app/services/risk_engine.py`, not a black box. Point out the row's "glacial hazard context" badge too (`glof_contribution_pct`/`tier`) — real, but explicitly labelled advisory, not a flash-flood probability (see its tooltip / `docs/Limitations.md`). Point out the "SCS-CN runoff" badge as well — a real, standard NRCS TR-55 rainfall-runoff estimate computed from this village's actual soil texture and land cover, shown as a second, independent figure alongside the weighted score, never folded into it.

**3. Refresh to show live variance (15s).** Reload the risk table once or twice — scores visibly move a little each time, because the simulated providers generate a fresh reading on every request. This is a good complement to the What-If Simulator later in the walkthrough (Scene 5-6): this beat shows the system is genuinely live and non-static; that one shows a presenter can deliberately steer it.

**4. Upstream/catchment-awareness (20s).** Point at a downstream village (e.g. Rudraprayag) and its "upstream_rainfall" component — explain this is the max current rainfall among the real upstream-in-catchment villages (elevation-order proxy — honestly labelled as a proxy, not real sub-catchment routing, per `docs/Limitations.md`), which is what makes this catchment-aware rather than per-village-isolated.

**5-6. ORANGE/RED.** Scroll down to the What-if simulator and run a scenario with rainfall/soil pushed up (see "Reliably showing an ORANGE/RED moment" above) — the panel shows the jump from the village's real current level to the hypothetical one directly, clearly labelled as hypothetical. While there, also point at the SCS-CN runoff comparison beneath it — unlike the glacial-lake/glacier-melt fields, this figure genuinely responds to the same rainfall/soil-moisture overrides (a heavy-rain, saturated-ground scenario visibly raises the estimated runoff depth), a good concrete illustration that this is a real physical calculation reacting to the input, not a second scripted number. If you'd rather show a real (not hypothetical) HIGH/CRITICAL village instead, either pre-tighten thresholds per the fallback method above and point at its color-coded badge and the alert it generated (`GET /alerts`, a real DB-backed state machine, visible lower on the Authority page), or refresh a few times and note honestly that a real HIGH/CRITICAL moment is possible but not guaranteed on demand with default thresholds — either is a more honest beat than pretending the simulator's hypothetical result is a live reading.

**7. Lead-time estimate (15s).** Point at a village's lead-time figure and its note — explicitly labelled a Phase 10 prototype (straight-line distance ÷ one assumed flow velocity), `null` for a catchment-source village with nothing upstream, never a fabricated number for those.

**8. "Why is this village at risk?" (30s).** Use the Explain panel — pick a village, show the ranked, narrated real driver breakdown. State plainly this explains the ACTIVE baseline model's own components (Phase 9), not a SHAP explanation of the still-undeployed ML layer (Phase 5) — the panel's own `caveat` field says this too.

**9. Evacuation view (30s).** Show the Evacuation Routing panel — the new "every village at a glance" summary table (real `GET /evacuation/routes`, one call for the whole region) lets you point at every village's destination/distance/time/unsafe-hop-count at once before drilling into any one village's hop-by-hop detail (real `networkx` shortest path over the elevation-order topology to the catchment's real lowest-elevation village — explicitly not a real road network). Then the Evacuation Priority panel (transparent severity/lead-time/score sort). Say plainly this is decision support for authorized personnel, never an autonomous evacuation order.

**10. Sensor network + honest fallback story (30s).** Show the Sensor Network panel — 12 real nodes across both valleys, live online/stale/offline status. To demonstrate a real failure/fallback live: stop `iot/simulate_sensor_publisher.py` (Ctrl-C) and, after the configured online threshold elapses (`GIRIVARSHA_SENSOR_THRESHOLDS__ONLINE_MAX_SECONDS`, default 300s — worth lowering to ~20s in `backend/.env` just for this demo beat, same "real config, disclosed change" principle as the thresholds box above), refresh — a node visibly flips to `stale`, and the risk engine genuinely falls back to the configured provider for that village (this fallback is real and wired, not just described — see `docs/IoT_Architecture.md`). **State clearly that this does not currently raise or lower the risk score's confidence in this demo build** — the reason isn't that sensors aren't wired in (they are); it's that this build's demo sensors self-report `source: "simulated"`, so swapping a simulated sensor reading for a simulated provider reading doesn't change the data-source tier either way. Only a real (`source: "real"`) sensor feed would move `confidence_pct`. If you also want to show the confidence-affecting fallback path (`ProviderUnavailableError` → honest degrade to the SIMULATED tier), that's `tests/backend/test_failure_modes.py::test_risk_computation_survives_a_real_provider_outage` (Phase 13) — showing the test passing live is a legitimate way to demonstrate this without needing a live Open-Meteo outage on stage.

**11. Historical Event Replay (30s).** Step through either seeded disaster (2013 Kedarnath, 2021 Reni/Tapovan) — real, individually-cited sub-events, each honestly labelled by how precisely it's documented (`exact_time`/`approximate`/`date_only`), not a fabricated minute-by-minute account.

**12. Close (20s).** The differentiation table and the five things to remember (`docs/Product_Positioning.md`), then explicitly pull up `docs/Limitations.md` for ten seconds — stating your own limitations plainly, unprompted, builds more trust than omitting them.

## If something goes wrong live

- **"Backend unreachable" in the header** — check `uvicorn` is still running and the frontend is on an allowed CORS port (5173 or 3000).
- **Map area is blank/gray** — confirmed network-dependent (OpenStreetMap tiles), not an app bug; rehearse Scene 1 on the actual presenting machine's network beforehand.
- **Sensors show 0/N online** — the simulator (`iot/simulate_sensor_publisher.py`) isn't running, or hasn't published yet; give it ~10-15 seconds after starting.
- **A reviewer asks to see a failure mode live** — `docs/Failure_Mode_Testing.md` lists all nine, each with a real, fast, runnable test; running `pytest tests/backend/test_failure_modes.py -v` live is itself a legitimate demo beat for a technical audience.
