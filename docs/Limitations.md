# Limitations

Honest, current, as of **Phase 5**. This file is updated every phase — see `docs/Future_Work.md` for what closes each gap.

## What's real right now

- The FastAPI backend boots, serves `/health`, `/version`, one working simulated-data endpoint, and returns honest `501`s for everything not yet built.
- `/villages`, `/villages/{id}`, `/catchments`, and `/historical-events` are real, DB-backed, and return real seeded data for the Mandakini valley pilot region (verified with `pytest`, 10/10 backend tests passing, including DB-dependent tests).
- A real PostgreSQL 16 + PostGIS 3.4 database is running with the full 14-table schema, applied via Alembic migration (not just `create_all`), with correct GiST spatial indexes on every geometry column.
- The React/Vite/TS frontend builds (`tsc -b && vite build` succeeds), renders a real Leaflet map of the pilot villages and a real catchment-topology panel, and live-polls the backend for status (verified with 6/6 vitest component tests passing).
- The GIS catchment-delineation *algorithm* (D8 flow direction/accumulation/watershed, via pysheds) is real, runnable code, verified against a synthetic DEM (2/2 pytest passing) — see `docs/GIS_Methodology.md`.
- `docker-compose.yml` describes the intended local topology but **has not been run** — no Docker daemon was available in the sandbox this was built in. This is a known gap, not a hidden one.

## What's real but incomplete (Phase 2 specifics)

- **4 of 6 pilot villages have approximate, not surveyed, coordinates.** This sandbox's network egress blocked direct calls to OpenStreetMap/Nominatim/Overpass (verified — `connect_rejected` on every attempt). Real elevations and real river-order topology were sourced via web search/fetch of Wikipedia articles; the 4 villages without a stated exact coordinate were placed by interpolating along the documented river path between the two villages that do have surveyed coordinates (Kedarnath, Rudraprayag). Every row is labelled `coordinate_precision: approximate` or `surveyed` — this is never blurred, and the map colour-codes markers by this field rather than presenting all six the same way. **Getting real survey-grade coordinates (OSM extract, Bhuvan/Survey of India, or field GPS) is the top item for whoever continues this.**
- **Sonprayag's elevation (1360m) is an unverified estimate**, not sourced from a citation — flagged explicitly in `scripts/seed_pilot_region.py` and `docs/Data_Sources.md`.
- **Only 1 historical event is seeded** (the 2013 Kedarnath disaster) — enough to prove the schema and pipeline work, nowhere near enough to train a statistically valid ML model. This is exactly the "sparse historical event labels" limitation problem-statement item 40/item 9 asks to be explicit about.

## What's real but incomplete (Phase 3 specifics)

- **Micro-catchment topology is real (river order); polygon boundaries are still not.** `has_polygon_geometry` remains honestly `false` on the seeded catchment, and the frontend map draws no fake catchment boundary — only real village points and a dashed elevation-order line explicitly labelled "not the real river course."
- **The DEM-based delineation pipeline is real code, only network-blocked, not unwritten.** `gis/delineate_catchment.py`'s actual flow-accumulation/watershed algorithm is tested and passing against a synthetic DEM. What's missing is the DEM download step (`download_srtm_dem()`), which needs an OpenTopography API key and outbound internet access this sandbox doesn't have (confirmed: direct attempt returned `403 Forbidden` at the egress proxy). `docs/GIS_Methodology.md` has the exact commands to finish this on a machine with normal internet access — no code changes needed.
- **The "river" line on the map is a visual aid, not real geometry.** It connects the 6 villages in elevation order to suggest downstream direction; it is explicitly labelled in the map legend as not the real river course, since no real digitised stream line exists yet.

## What's real but incomplete (Phase 4 specifics)

- **Confidence is honestly capped around 40% BY DEFAULT — but this is now opt-in, not fixed.** `confidence_pct` is a weighted average of each input's source-tier trust (real > derived > simulated). Out of the box, rainfall/soil-moisture are still SIMULATED, so confidence stays low — but as of Phase 9-10, setting `GIRIVARSHA_ACTIVE_RAINFALL_PROVIDER=real`/`GIRIVARSHA_ACTIVE_SOIL_PROVIDER=real` (`backend/.env`) switches those inputs to Open-Meteo's live forecast API (free, no key) and confidence genuinely rises (~40% → ~85%+), with no change to the formula. This HTTP call could not be verified from the sandbox this was built in (network-blocked, same as the OpenTopography DEM download) — see docs/Technical_Notes.md's "Real weather data" section for the one-line way to verify it yourself. Separately, Phase 8's real sensor ingestion pipeline (`GET /sensors`) IS now wired into these providers (a later follow-up, see the "Phase 8+ follow-up" section below and `docs/Future_Work.md`) — a village with an online sensor uses it ahead of the provider, though this build's demo sensors still declare `simulated`, so it doesn't raise confidence on its own here.
- **The risk score itself is not validated against real outcomes.** There is exactly one historical event in the whole pilot region (2013 Kedarnath). The baseline's weights (`GIRIVARSHA_RISK_WEIGHTS__*`) are a documented, reasonable starting point — not a fitted or tuned result. `GET /api/v1/version` reports `active_model.trained: false` for exactly this reason.
- **"Upstream" is an elevation-order proxy, not real catchment sub-topology.** With only one micro-catchment seeded so far, the engine treats any other village in the same catchment at higher elevation as "upstream" — which matches the real, documented river order for this pilot region, but is a simplification that should be replaced with real per-catchment topology once multiple micro-catchments exist. Documented in the code (`app/services/risk_engine.py`) and in `docs/GIS_Methodology.md`. The same proxy is reused by Phase 10's lead-time estimator (`app/services/lead_time.py`), so it inherits this same limitation.
- **Alerts have no delivery mechanism yet** (no SMS/push/siren) — `GET /alerts` is a real, DB-backed state machine (open/resolved, level transitions), but nothing currently *notifies* anyone; that's part of later phases.

## What's real but incomplete (Phase 5 specifics)

- **The ML layer is NOT deployed, on purpose.** `ml/train.py`'s pipeline (feature ladder, temporal split, XGBoost, honest metrics) is real, tested, and runs correctly — but only against synthetic data (`ml/generate_synthetic_training_data.py`), because there is exactly one real historical event in the pilot region. `GET /api/v1/risk/*` uses only the Phase 4 baseline; `GET /api/v1/version`'s `ml_layer.status` says `not_deployed` and explains why, rather than silently shipping an unvalidated model.
- **The synthetic run doesn't show a clean "more sources = better" result**, and that's reported honestly in `docs/ML_Methodology.md` rather than massaged into a nicer-looking story — all four models (rainfall-only through all-sources) score similarly (AUC ~0.66) on the synthetic ground truth. This is a real, reproducible finding about this specific synthetic setup, not a claim about real-world flood prediction, which the data simply can't support yet either way.
- **What would unblock a real model**: real historical flash-flood/landslide event records for this or comparable catchments — see `docs/ML_Methodology.md`'s closing section for where those might come from.

## What's real but incomplete (Phase 12 follow-up: real ML training-data assembly)

- **The ML layer is still NOT deployed — this work moved the data problem forward, it did not solve it.** 36 real, cited positive events (up from 1) is genuine progress, but `ml/train_real.py`'s own honest metrics (ROC-AUC 0.649, false-negative rate 58.3%) are explicitly not good enough to put behind a life-safety warning — see `docs/ML_Methodology.md` for the full reasoning. `GET /api/v1/version`'s `ml_layer.status` is unchanged.
- **The 36 trainable real events are not specific to either pilot valley.** They're drawn from a global GLOF inventory's Himalayan-arc subset (India, Nepal, Bhutan, Pakistan), scattered across very different elevations (2,100-5,000m) than either the Mandakini or Chamoli catchment's villages (900-3,600m). A model trained on this captures general "does heavy rain precede a GLOF" signal across the Himalaya, not anything localized to the two seeded valleys.
- **No real soil-moisture or upstream-catchment-rainfall features exist for this dataset.** Only rainfall (from NASA POWER) and elevation are real and available — this dataset can't be compared feature-for-feature against the Phase 4 baseline's 4-component formula.
- **"Negative" examples mean "not recorded in the source inventory," not "confirmed no event occurred."** Small or undocumented GLOFs may be missing from the source database — a real, disclosed sampling bias, not something this project can fix without a more exhaustive ground-truth source.
- **5 of 41 candidate positive events couldn't be backfilled at all** — they predate 1981, before NASA POWER's MERRA-2 reanalysis coverage begins. They're honestly skipped (not counted as negatives, not assigned fabricated rainfall), visible in `ml/backfill_real_weather.py`'s own console output.
- **404 real, cited India hill-state flood/landslide events have no coordinates** in their source dataset (India Flood Inventory is district-level, not point-located). 311 of these were later real-geocoded (see the follow-up #2 section below) — this bullet's original 144-row run predates that and never force-geocoded anything, which is why the number was 0 at the time.
- **`rainfall_intensity_mm_hr_proxy` is a labelled approximation**, not a real sub-daily measurement — it's each day's total rainfall (from NASA POWER, a real daily-resolution product) divided by 24, standing in for the risk engine's mm/hr intensity component. Real flash floods are usually driven by rain concentrated in a few hours, not spread evenly across a day, so this proxy under-represents true peak intensity.

## What's real but incomplete (Phase 12 follow-up #2: geocoding + expanding the real ML dataset to 1,071 rows)

- **The ML layer is STILL not deployed.** A real, meaningfully better false-negative rate (58.3% → ~27.3% mean across 4 CV folds) is genuine further progress, not a deployment threshold crossed — missing roughly 1 in 4 real events, with real fold-to-fold variance (std 0.116) meaning some periods would miss noticeably more, is still not acceptable for a life-safety warning. `GET /api/v1/version`'s `ml_layer.status` remains unchanged.
- **A single temporal train/test split on this expanded dataset is measurably misleading, and this project caught and disclosed it rather than reporting the flattering number.** The IFI source documents recent years (2022-2023 especially) far more thoroughly than older ones, so a "last 25% by date" split lands in a recent, ~77%-positive tail — nothing like the full dataset's ~32% positive rate. `ml/train_real.py` now reports a 4-fold expanding-window cross-validation as the headline metric specifically because of this, with the single split kept only for comparability to the prior 144-row run and explicitly flagged as non-representative. See `docs/ML_Methodology.md` for the full numbers.
- **927 of the 1,071 combined rows carry DISTRICT-CENTROID coordinates, not point coordinates.** These are real OpenStreetMap Nominatim geocodes of `(state, district)` — genuinely real, not fabricated — but coarser than the original 144-row dataset's lake/village-level precision. For a large district, the actual flood/landslide site could be tens of kilometres from the centroid used to pull rainfall. `ml/train_real.py`'s per-model `single_split_by_coordinate_precision` breakdown exists to surface this, though the point-precision stratum only has 12 rows in that split — too few to draw a confident point-vs-district comparison from; it's reported for transparency, not as validated evidence either way.
- **72 of the 404 candidate events remain honestly uncoordinated** — they were recorded against 2-27 districts at once, and collapsing a multi-district event to a single point would misrepresent the source data's own precision more than leaving it out. No forcing, no first-district shortcut.
- **21 of the 332 single-district events could not be geocoded at all** — Nominatim genuinely had no match for that district name (a data-entry variant, a renamed/reorganized district, etc.) — honestly dropped, not guessed at.
- **XGBoost was tried for the first time on real data here** (skipped entirely in follow-up #1 at N=144) and turned out to have a WORSE mean false-negative rate than logistic regression (0.343 vs 0.273) — a real finding that more model complexity didn't automatically help at this data volume, reported honestly rather than only showing the model that looks more sophisticated.
- **Negative examples still mean "not recorded in the source inventory," not "confirmed no event occurred"** — same caveat as follow-up #1, now covering two source inventories (GLOF + IFI) instead of one.

## What's real but incomplete (Phase 9-10 specifics)

- **Explainability (Phase 9) explains the baseline, not the ML layer.** `GET /model/explanation/{id}` ranks and narrates the Phase 4 baseline's own real components — it is NOT a SHAP explanation of the undeployed Phase 5 ML model, because there is no deployed model to compute SHAP values against. Every response's `caveat` field says so explicitly.
- **Lead-time estimation (Phase 10) is a straight-line, single-velocity prototype, not validated hydraulic routing.** `lead_time_minutes`/`lead_time_note` on `GET /risk/*` divide haversine (as-the-crow-flies, not river-course) distance to the nearest upstream village by one conservative, citably-sourced assumed flow velocity (5 m/s) for the whole valley. Real per-reach hydraulics (channel geometry, slope, discharge — HEC-RAS or equivalent) is future work, tracked in `docs/Future_Work.md`. Honestly `null` for a catchment-source village with nothing upstream.
- **Real weather providers (Open-Meteo) are opt-in and unverified from this build environment's own network** — see the confidence bullet above. The parsing/error-handling logic is unit-tested (`tests/backend/test_providers.py`) against a mocked response shape, and the honest-fallback path (real provider unreachable → app doesn't crash, degrades to the same simulated-tagged default any provider failure already uses) was verified live in this sandbox — but the live HTTP call itself needs verification on a normal internet connection.

## What's real but incomplete (Phase 11 specifics)

- **The region registry is real and holds two independently-sourced valleys, not one hard-coded pilot region.** `GET /regions` returns 5 real, named, documented Himalayan valleys: 2 `active` (village-level data seeded — Mandakini Valley and the Chamoli Disaster Valley) and 3 honestly `planned` (real, cited, flash-flood/GLOF-prone valleys — South Lhonak/Teesta, Jhelum/Kashmir, Beas/Kullu-Manali — that the schema and API already support but that have **not** been sourced to village level; `village_count` is `0` for all three, never a placeholder number). `?region_id=` scopes `/villages`, `/catchments`, and `/risk/map`; omitting it keeps every pre-Phase-11 caller's behaviour unchanged. See `docs/Region_Onboarding.md` for exactly what moving a `planned` region to `active` requires.
- **The Chamoli Disaster Valley (4 villages: Reni, Tapovan, Vishnuprayag, Joshimath) is real and, on coordinate precision, better-sourced than Mandakini** — all 4 villages are `surveyed` (vs. Mandakini's 4-of-6 `approximate`), backed by Wikipedia infoboxes or the peer-reviewed GEER Association engineering reconnaissance report on the real 7 February 2021 disaster. One real historical event is seeded (the 2021 rock-ice-avalanche flash flood, ~200 dead), with real citations.
- **Known, concrete example of the elevation-order "upstream" proxy's limitation: Joshimath.** Joshimath's real Wikipedia elevation (1,875m) is the *town's* position on a terrace above the river — not the river's true elevation at the immediately-adjacent Vishnuprayag confluence (1,372m), which is actually upstream of Joshimath along the real river course. Because the risk/lead-time engine's "upstream" proxy (see the Phase 4 bullet above) orders purely by elevation within a catchment, it picks Joshimath — not Vishnuprayag — as Tapovan's "nearest upstream village," which is backwards from the real river topology. This was deliberately **not** patched by adjusting Joshimath's elevation number (that would mean showing a fabricated figure to make the app's proxy look cleaner); it's surfaced here, in `docs/Data_Sources.md`, and inline in `scripts/seed_chamoli_valley.py`'s docstring and Joshimath's own `provenance` field instead. It is the clearest concrete evidence yet that real per-catchment hydrological routing (not an elevation-order proxy) is needed before lead-time/upstream figures should be treated as more than a rough prototype — tracked in `docs/Future_Work.md`.
- **Sensors and alerts are now region-scoped server-side too (user-requested follow-up — since closed).** `GET /sensors` and `GET /alerts` both accept `?region_id=`, using the same real Sensor/Alert → Village → MicroCatchment → Region join `/villages`, `/catchments`, and `/risk/map` already use — see "Server-side region filtering for sensors and alerts" below for the full writeup. Omitting the param keeps every existing caller's behavior unchanged.

## What's real but incomplete (Phase 12 specifics)

- **Evacuation routing's hop TOPOLOGY (which villages count as consecutive waypoints) is still the elevation-order proxy** — real village positions, not real trail branching structure. **As of a later follow-up (see the dedicated section below), each hop's DISTANCE now comes from a real OpenStreetMap road/trail path wherever one actually covers both endpoints** — a real improvement, but only a partial one: real coverage isn't universal even within this pilot data, and a hop with no real coverage still falls back to the original straight-line distance. Every response's `note` and each hop's own `road_note` field say this explicitly, and it is never presented as turn-by-turn guidance.
- **`estimated_minutes` rests on one assumption: Naismith's Rule's 5 km/h walking pace**, applied uniformly to every hop regardless of real terrain, slope, group composition (elderly, children, injured), or emergency conditions — all of which would change real evacuation time meaningfully. It is a documented order-of-magnitude planning figure, not a measured or validated one for this terrain.
- **The `unsafe` hop flag is a derived heuristic, not real hazard data.** It fires when either hop endpoint's *live*, freshly-computed risk level is `HIGH`/`CRITICAL` — reusing data the app already trusts (the Phase 4 baseline), not a new source of ground truth about road conditions, landslide blockage, or bridge integrity.
- **`GET /evacuation/priority`'s ranking is a transparent sort, not a validated triage algorithm.** It orders by risk severity, then lead-time, then risk score — a reasonable, explainable default, not something calibrated against real evacuation-outcome data (none exists to calibrate against).
- **Historical event replay's timelines are genuinely sparse, not artificially thin.** Only 7 (Kedarnath) and 3 (Reni/Tapovan) sub-events are seeded per disaster because that's what the cited public sources actually document with enough specificity to cite individually — not a deliberately small sample from a larger available record. Most entries are `date_only` or `approximate`; only a handful carry an `exact_time`, and that honesty is the point (see `docs/Architecture.md` for the timezone-conversion care this required). Only the two disasters already seeded elsewhere in the app (Kedarnath, Reni/Tapovan) have a timeline at all — `GET /replay/events` simply omits any event without one.

## What's real but incomplete (Phase 12 follow-up: glacial-lake proximity)

- **Distance alone is not a validated GLOF hazard indicator.** `glacial_lake_distance_km` is a real straight-line distance to the nearest of 4,881 real, satellite-mapped lakes (Zhang et al. 2023) — it does not account for lake type (moraine-dammed lakes are the higher-hazard category; the source data has this field but this indicator doesn't use it yet), dam material, lake volume, or downstream channel/slope, all of which materially affect real GLOF hazard. A village 5km from a small, stable bedrock-dammed lake is not equivalently at-risk to one 5km from a large moraine-dammed lake — this field can't yet tell the two apart.
- **This is why it's advisory-only, never folded into `risk_score`/`risk_level`.** There is no real calibration data (no labelled outcomes) to say how much weight lake proximity should carry relative to the baseline's existing 4 components — the same honesty problem already documented for the undeployed ML layer above. An uncalibrated 5th weight would look more precise than it is.
- **Straight-line, not flow-path, distance.** Same caveat as lead-time's haversine distance — a lake 5km away in a straight line may be much farther (or, in principle, closer) along the actual valley a GLOF would travel down. No downstream flow-path modeling exists yet.
- **The underlying inventory is a single 2020 snapshot**, not a live feed — new lakes that have formed, or existing lakes that have grown, since 2020 are not reflected. The source dataset does include earlier snapshots (1990/2000/2010/2015) for anyone wanting to study lake growth over time, but only 2020 is used here.
- **`MAX_RELEVANT_DISTANCE_KM = 100`** is a documented, round, unfitted cutoff — a village more than 100km from a mapped lake gets an honest "too far to be a meaningfully nearby concern" note rather than the technically-nearest lake regardless of how far away it actually is.

## What's real but incomplete (Phase 8+ follow-up, user-requested: wiring sensors into the risk engine)

- **This closes the "sensors don't affect risk confidence" gap flagged as a Phase 14 finding**, but only in this build's demo conditions the fix doesn't itself change confidence numbers. `risk_engine.py` now genuinely checks for a fresh (`online`) sensor reading before falling back to the configured provider — verified end-to-end (a village with an online sensor now shows a driver description naming the exact device, e.g. "...from this village's live sensor (sensor:esp32-kedarnath-rain-01)"). But this build's demo sensors (`iot/simulate_sensor_publisher.py`) still declare `source: "simulated"`, honestly, because no physical hardware exists here — so using a sensor reading instead of a provider reading does NOT currently raise `confidence_pct`, since both are SIMULATED-tier. Confidence would only rise if a real sensor (or a firmware update to `iot/simulate_sensor_publisher.py` that declared `source: "real"`, which would itself be dishonest without real hardware behind it) reported `source: "real"`.
- **A village with more than one sensor of the same type picks the most-recently-seen one, not an average or a fusion.** No pilot village is currently double-sensored, so this hasn't been exercised with real data — it's a defensive design choice (avoiding a `MultipleResultsFound` crash) verified only against a synthetic two-sensor scenario in tests, not a considered fusion strategy.
- **Found and fixed a second, smaller honesty gap while wiring this in**: `upstream_rainfall`'s `source` tag was hardcoded to `SIMULATED` regardless of what actually produced the value used — meaning even with `GIRIVARSHA_ACTIVE_RAINFALL_PROVIDER=real` (or now, a real sensor) active for an upstream village, that component's contribution to `confidence_pct` stayed pinned at the SIMULATED tier. Now tagged from whichever upstream village's reading actually produced the max value used.
- **Only rainfall and soil-moisture sensors are wired in** — the schema also defines `WATER_LEVEL`/`TILT` sensor types (unused by any seeded node) and the risk engine has no component for either yet; wiring those in would need both real sensor hardware/simulation for those types and a new risk-engine component, neither of which exists.

## What's real but incomplete (What-If Simulator follow-up, user-requested)

- **`POST /simulate` is real, and reuses the exact same formula — there is no separate "simulation model."** It calls `compute_risk_for_village()` (the same function `GET /risk/{id}` calls) twice: once unmodified for the real current baseline, once with the given rainfall/soil-moisture override(s) substituted in via new `rainfall_override`/`soil_override` parameters. Nothing about the weights, thresholds, upstream logic, or historical-susceptibility calculation is duplicated or diverges between a real call and a simulated one.
- **Only this village's own rainfall/soil-moisture input can be overridden — not an upstream village's, and not historical susceptibility.** A presenter cannot currently simulate "what if it's raining hard upstream" for a downstream village's `upstream_rainfall` component; that component still reflects whatever the upstream villages' real current sensors/providers report. Extending overrides to upstream villages would need a list-of-village-overrides request shape, not built here.
- **An override is always tagged `DataSource.SIMULATED`, regardless of what this village's real current data source actually is.** A presenter-typed number is not a live observation, so it is never presented as REAL or DERIVED even if, say, a real sensor happens to be online for that village at the time — see `SimulationOut.note`, always rendered verbatim in the frontend panel rather than paraphrased.
- **Zero persistence, by design.** `compute_risk_for_village()` was already documented as side-effect-free (it doesn't write to the DB); `POST /simulate` calls it directly and never calls `persist_prediction()`/`sync_alert_for_village()` the way `GET /risk/map`/`GET /risk/{id}` do. A what-if run cannot create a fake `RiskPrediction` row or a fake alert — verified in `tests/backend/test_simulate.py::test_simulate_never_persists_or_creates_an_alert`.
- **Values are bounded to plausible physical ranges (`rainfall_mm_hr` 0-500, `soil_moisture_pct` 0-100), not arbitrary.** This is a basic sanity guard, not hydrological validation — the app has no model of what rainfall rate is physically plausible for a specific Himalayan micro-catchment; the caps are round, generous, documented bounds, same "conservative, not fitted" spirit as `RAINFALL_CAP_MM_PER_HR` elsewhere in `risk_engine.py`.

## What's real but incomplete (glacier melt-rate follow-up, user-requested: "incorporate the melting rate of nearby glaciers into the risk score and how probable a flash flood is based on nearby glacial data")

- **`glacial_melt_rate` is a genuine 5th weighted risk-engine component, but its weight (0.10) is still a documented, non-calibrated starting point, not a fitted result** — same honesty gap as every other weight in `RiskWeights` (no labelled flash-flood outcome dataset exists to fit against). Rainfall/soil moisture were rebalanced down slightly (0.35→0.30, 0.25→0.20) to make room; upstream rainfall and historical susceptibility were left untouched. See `app/core/config.py`'s `RiskWeights` docstring for the exact reasoning.
- **This treats glacier melt rate differently from raw glacial-lake distance, on purpose — but that distinction is itself a judgment call, not a proven one.** The reasoning (a glacier's own recent mass-balance rate is a narrower, more physically-direct meltwater/instability signal than an unqualified "how close is the nearest lake" proxy) is stated in `app/services/glacial_melt_hazard.py`'s module docstring, but nobody has validated that this component actually improves real flash-flood prediction — it is a defensible design choice given the real data available, not a claim of demonstrated predictive value.
- **Normalization bounds are derived from the loaded regional dataset's own 5th-95th percentile distribution (not hand-picked), but the dataset itself is a fixed snapshot (2021-2025 mean).** A glacier's melt rate genuinely varies year to year; this is "how fast was it melting on average over the last 5 real observed years," not a live, continuously-updating measurement — the nearest analogue to `glacial_lake_distance_km`'s "2020 snapshot, not a live feed" caveat above.
- **The GLOF contribution indicator (`glof_contribution_pct`/`glof_contribution_tier`) is explicitly NOT a calibrated statistical flash-flood probability**, despite answering a question phrased as "how probable." It is a disclosed, equal-weighted heuristic blend of two real inputs (lake proximity + melt rate) — the 50/50 weighting between them is itself an arbitrary, stated choice, not fitted to any outcome data, and every response's `note` field says this explicitly rather than presenting a bare, probability-looking number. Same restraint the glacial-lake-proximity section above already applies to a single input; this extends it to a two-input blend rather than abandoning it once two real signals were available to combine.
- **Both new fields inherit the underlying dataset's 100km relevance cutoff and straight-line-distance caveat** from `glacial_lake_proximity.py`/`glacial_melt_hazard.py` (see those sections above) — nothing about combining the two signals fixes either module's own individual limitations.

## What's real but incomplete (evacuation-routes follow-up, user-requested: "an evacuation route for each village")

- **Every seeded village already had its own real, computable route — `GET /evacuation/routes` doesn't add new routing logic, it just calls the existing per-village computation (`evacuation_route()`) for every village in one request** instead of requiring a client to look each one up individually via `GET /evacuation/route/{id}`. Every limitation already documented in the Phase 12 evacuation-routing section above (no real road network, elevation-order proxy topology, Naismith's-Rule walking-pace assumption, heuristic unsafe-hop flag) applies identically here — nothing about batching the computation changes what's real vs. simplified about any individual route.
- **The Authority dashboard's evacuation panel now shows this summary as a table above the existing per-village detail view**, letting an authority user scan every village's destination/distance/time/unsafe-hop-count at a glance rather than clicking through villages one at a time; clicking a row still opens that village's full hop-by-hop breakdown below, so no detail was traded away for the summary.

## What's real but incomplete (SCS-CN rainfall-runoff follow-up, user-requested: "a real SCS-CN rainfall-runoff layer... would be the highest-value next addition")

- **This is a real application of a standard, decades-old (USDA-SCS, 1972; still the basis of the modern NRCS TR-55 manual) hydrological method to real per-village soil (ISRIC SoilGrids) and land-cover (ESA WorldCover) data — but it is deliberately NOT folded into `risk_score`/`risk_level`.** It is a second, independent, physically-grounded number shown alongside the weighted baseline score, per the user's own framing ("add this to the website" as an addition, not a replacement) and this project's existing restraint about not overclaiming what a single new signal proves — same discipline already applied to `glacial_lake_distance_km`.
- **TR-55's Curve Number tables are indexed by land use AND "hydrologic condition" (good/fair/poor ground cover) — WorldCover's 10m land-cover classes carry no condition field at all.** This module defaults every land-cover class to one stated representative condition (documented per-class in `scs_cn_runoff.py`'s `CURVE_NUMBER_TABLE`) rather than guessing at ground condition from satellite imagery alone — a real simplification, not a hidden one.
- **Antecedent Moisture Condition (AMC) — the method's own "how wet was the ground before this storm" input — was originally approximated from this village's CURRENT soil-moisture reading, not the standard 5-day antecedent-rainfall total**, because this app had no rainfall history to compute that from. A follow-up (see "What's real but incomplete (antecedent-precipitation-index follow-up..." below) has since added a real rainfall-history option; the soil-moisture proxy above remains the DEFAULT behavior and stays exactly as-is (same "real proxy, honestly labelled" idiom used elsewhere — upstream-catchment via elevation order, lead-time via straight-line distance) whenever the real antecedent data isn't active.
- **Rainfall depth is "the current instantaneous rate held for 1 hour," not a real hyetograph.** SCS-CN needs a storm DEPTH (mm), and this app only has a live rate (mm/hr); multiplying by an assumed 1-hour duration is a deliberately modest, stated choice (`ASSUMED_STORM_DURATION_HOURS`), not a claim that any real storm actually lasts exactly that long.
- **The initial-abstraction ratio (lambda) is fixed at the method's own classic default, 0.20** — the original NRCS/TR-55 value, real and widely cited, but more recent literature suggests lambda=0.05 fits some regions better. Using the classic default is a defensible starting point, not a claim that 0.20 is validated for these specific Himalayan hill catchments.
- **The 15km relevance cutoff (`MAX_RELEVANT_DISTANCE_KM`) is tighter than the glacial-lake/glacier-melt modules' 100km**, because soil/land-cover inputs here are fetched per-village by `scripts/prepare_scs_cn_inputs.py`, not looked up in a large pre-fetched regional inventory — a genuinely new village more than a few km from an existing one needs that script re-run for it, not a distant neighbor's soil/land-cover silently borrowed.
- **Snow/ice and open-water land cover honestly return "not applicable," not a guessed number** — the SCS-CN method doesn't meaningfully apply to those surfaces. One real edge case this surfaced: Vishnuprayag's exact coordinate sits at a literal river confluence and samples as "permanent water"; the prep script resolves this with a disclosed windowed fallback (see `docs/Data_Sources.md`) rather than either crashing or silently reporting a fabricated number for a village that would otherwise appear to have no runoff estimate at all.
- **The What-If Simulator's SCS-CN comparison fields (`baseline_scs_cn_*` / `simulated_scs_cn_*` on `POST /simulate`) genuinely respond to rainfall/soil-moisture overrides, unlike the glacial-lake/glacier-melt advisory fields, which don't depend on those inputs at all** — this happens automatically because the same already-resolved rainfall/soil values (which reflect any active override) feed both the weighted score and this estimate, not because of any special-cased simulation logic.

## What's real but incomplete (real road/trail network follow-up, user-requested: "let's do the real road/trail data")

- **Real road/trail coverage is genuinely uneven, even within this pilot data — not just "not yet extended everywhere".** A concrete, disclosed example found while building this: Rambara's own seeded coordinate (`scripts/seed_pilot_region.py`) is explicitly labelled `coordinate_precision: "approximate"` — an interpolated point along the river corridor, not a surveyed one (Rambara was largely destroyed in the 2013 flood). That approximate coordinate's nearest real OSM node sits on a real `path`/`footway`/`bridleway` trail fragment that this build's fetched Mandakini-valley extent shows as a SEPARATE connected component from the rest of the network — Kedarnath and Gaurikund's own nearest nodes both sit in the same large, 56,622-node component, but nothing in the fetched data connects Rambara's fragment to it. Both the Kedarnath→Rambara and Rambara→Gaurikund hops honestly fall back to the straight-line proxy as a result, while the Kedarnath→Rambara→Gaurikund chain's real end-to-end trek (skipping the interpolated point) can be independently confirmed as real and connected: `find_real_route` returns an 11.64km path straight from Kedarnath to Gaurikund. Whether this is a genuine gap in OSM's own trail mapping near the old Rambara rest-stop, or a real trail that exists just outside this build's fetched bounding box, hasn't been independently checked — either way, this is exactly the kind of thing an approximate, non-surveyed coordinate can cause, and it's disclosed rather than silently masked by widening the snap tolerance until it "works."
- **The `ROAD_SNAP_MAX_METERS = 1500` tolerance is a judgment call, not a validated threshold.** It was chosen to accept the largest genuine snap distance actually observed in this pilot data (Sonprayag, ~1.04km — itself only `approximate` precision) while still rejecting a village nowhere near the fetched network. A future village with worse coordinate precision, or one near a real road that just happens to be thin on OSM tagging, could snap outside this tolerance and honestly fall back rather than being force-matched to a distant, wrong road.
- **The fetched network only covers two bounding boxes around the two pilot valleys** (`scripts/prepare_road_network_data.py`'s `REGIONS` dict) — a route between the two valleys, or to any unseeded village, simply isn't covered; `find_real_route` returns `None` honestly rather than guessing at a road that might exist outside the fetched extent.
- **No elevation/slope is attached to any real edge**, so `estimated_minutes` still uses the same single, uniform Naismith's-Rule walking pace regardless of whether a real hop is flat highway or a steep mapped trail — real per-segment terrain-aware timing would need real elevation data joined to each OSM way, not built here.
- **No real-time road-condition data exists for any of this** — a real mapped road segment could be washed out, landslide-blocked, or under construction right now, and this build has no way to know. The `unsafe` hop flag is unchanged by this follow-up: still a derived heuristic from live village risk levels, not real road-hazard reporting.
- **This sandbox's connection to the Overpass API is genuinely flaky** (`overpass-api.de` reset the connection on the large majority of attempts during development; the `overpass.kumi.systems` mirror rate-limited aggressively under repeated retries) — `scripts/prepare_road_network_data.py`'s retry loop across both endpoints, plus a local raw-response cache (`data/raw/osm_overpass_cache/`, gitignored, regenerable), were both needed to get a complete fetch. A production environment with a normal connection would likely need far fewer retries, but the retry loop is a correct thing to keep regardless.

## What's real but incomplete (rainfall intensity-duration threshold follow-up, user-requested, from this project's own competitive-landscape research)

- **The source study's own validated event-duration range is 24 hours — this is used as a hard honest boundary, not extrapolated past it.** A village whose current (low, above-floor) rainfall rate would only cross the published curve after more than 24 hours is reported as `"not_indicated_within_24h"`, not given a fabricated multi-day countdown the study never actually validated.
- **Applicability is a disclosed two-tier judgment call, not a second independent study.** The Chamoli Disaster Valley genuinely is the region Kanungo & Sharma (2014) studied — a direct fit. The Mandakini valley is a *different* catchment in the same broader Garhwal Himalaya climatic/geological zone; applying the same curve there (`applicability="regional_proxy"`) is the same "real proxy, honestly labelled" idiom already used elsewhere in this app (elevation-order upstream, straight-line lead time) — not a claim that the study's own dataset covers Kedarnath, Rudraprayag, or any other Mandakini village.
- **This is a constant-rate model, not a hyetograph or a forecast.** It answers "if today's current rate continued steadily, how many hours until it crosses the published threshold" — a real storm accelerates and decelerates, and this number says nothing about whether the rate actually will continue. `rainfall_threshold_status="threshold_exceeded"` means the current instantaneous rate already exceeds what the study associates with triggering a landslide even for a short event, not that a landslide is occurring or imminent.
- **Below the study's own 0.87mm/hr floor, no crossing duration is computed at all** (`status="below_floor"`, `hours_to_threshold=None`) rather than extrapolating the curve into a regime the paper's own dataset never actually tested.
- **Deliberately NOT folded into `risk_score`/`risk_level`** — a third, independent, transparently-derived figure shown alongside the weighted score and the SCS-CN estimate, same restraint already applied to `glacial_lake_distance_km` and `scs_cn_runoff_depth_mm`.
- **The What-If Simulator's comparison fields (`baseline_rainfall_threshold_*` / `simulated_rainfall_threshold_*` on `POST /simulate`) genuinely respond to a rainfall override**, unlike the glacial-lake/glacier-melt advisory fields — same mechanism as the SCS-CN comparison above (the same already-resolved, possibly-overridden rainfall value feeds both).

## What's real but incomplete (antecedent-precipitation-index follow-up, user-requested)

- **NASA POWER's most recent ~7-8 days of daily rainfall consistently return its own `-999.0` "not yet processed" fill value — a genuine source-side reporting lag, not a fetch bug.** `antecedent_rainfall.py` fetches a wide 35-day window and computes its 5/10/20-day sums from the most recent real day actually available, never assuming that's "today" — the exact lag (e.g. "8d ago") is stated plainly in every result's `note`, never hidden or silently backfilled with an estimate.
- **A caught-and-fixed design bug worth documenting**: `get_antecedent_rainfall()` always returns a usable result (real or a clearly-labelled simulated fallback) — it never returns `None`. An earlier draft of the `scs_cn_runoff.py` wiring checked only "is a result present," which would have made even the DEFAULT `simulated` setting silently replace the existing soil-moisture-proxy AMC classification with a different (but equally unvalidated) simulated one — a stealthy change to every existing response's behavior with no real accuracy gain. Fixed before any test caught it as broken, by gating the override specifically on `antecedent_rainfall_source == "real"`; `test_simulated_antecedent_rainfall_does_not_override_soil_moisture_proxy` guards against a regression.
- **The AMC-classification thresholds (5-day sum, season-dependent) are the classic SCS/NRCS values from Chow, Maidment & Mays' *Applied Hydrology*** — the same textbook already cited for the SCS-CN method's other constants (lambda=0.20) — not independently validated for these specific Himalayan hill catchments.
- **Growing-season vs. dormant-season is a calendar-month rule (Apr-Oct vs. Nov-Mar), a disclosed simplification** — real growing-season boundaries vary by elevation, crop, and year; a fixed calendar cutoff is the same "defensible stand-in, not a claim of precision" idiom used throughout this project.
- **Deliberately NOT folded into `risk_score`/`risk_level` directly** — it feeds `scs_cn_amc_class` (itself already a second, independent, never-scored figure) rather than the weighted baseline formula.
- **On `POST /simulate`, this is a single figure, not a baseline/simulated comparison pair** — unlike the SCS-CN and rainfall-threshold fields above, antecedent rainfall is real/simulated rainfall HISTORY, genuinely independent of the rainfall/soil-moisture what-if overrides, so showing it as if it changed between "baseline" and "hypothetical" would misrepresent what it is; `antecedent_rainfall_note` states this plainly, and `test_simulate_antecedent_rainfall_is_independent_of_overrides` guards it.
- **Cached once per village per calendar day** (`@lru_cache` keyed on rounded coordinate + today's date), same discipline as the earlier `/risk/map` N² performance fix — accepted as a first-request-of-the-day cost when real mode is active, not a repeat fetch per request.
- **Deliberately scoped out of the Citizen view** — this is AMC-classification plumbing that improves the (already-shown) SCS-CN runoff figure invisibly; the citizen-facing text doesn't name antecedent rainfall directly, consistent with keeping that view in plain, non-technical language.

## What's real but incomplete (IoT device-authentication follow-up, user-requested)

- **This closes a real, previously-disclosed gap: `POST /sensor-reading` used to trust any request naming a registered `external_device_id`, with zero credential check.** Each sensor may now have a real per-device API key (`sensors.api_key_hash`, migration `5dbcb12077f4`) — a SHA-256 hex digest of a random `secrets.token_urlsafe(32)` value, compared with `hmac.compare_digest` (constant-time, so response timing can't leak the key byte-by-byte). No per-key salt, deliberately: the key is already a high-entropy random token, not a human password, so an unsalted hash carries no meaningful rainbow-table risk — the same reasoning GitHub/Stripe-style API tokens rely on.
- **`api_key_hash` is nullable, and that's a staged-rollout choice, not a permanently-optional design.** This column was added after real sensor rows already existed in this build's seeded databases, with no way to recover a plaintext key for any of them. A sensor with `api_key_hash IS NULL` is still accepted un-authenticated — the exact pre-migration behavior, unchanged, no retroactive lockout — until `scripts/rotate_sensor_api_keys.py` gives it a real key. `GET /sensors`'s new `authenticated` field reports this honestly per node, never hidden, so an operator can see at a glance which devices still need rotating.
- **The plaintext key is recoverable in exactly one place in this build environment: `iot/device_keys.json` (gitignored, never committed).** A real fleet would provision each device's key via its own hardware/config pipeline (flashing NVS, a factory-config service) instead of a shared file — this file exists only so `iot/simulate_sensor_publisher.py`/`iot/mqtt_bridge.py` can exercise the whole pipeline end-to-end without physical hardware. The firmware `.ino` files hardcode a placeholder `DEVICE_API_KEY` constant with an explicit comment that a real deployment must never provision keys this way.
- **This secures only the HTTP hop (`POST /sensor-reading`) — it does not add MQTT-broker-level authentication or TLS on either hop.** `mosquitto` still accepts any client exactly as before, and a key in transit (device→broker in the MQTT payload, bridge→backend in the `X-Device-Api-Key` header) is only as safe as the network it crosses. A production deployment reachable over the open internet would need TLS on both hops in addition to this — tracked in `docs/Future_Work.md`, not silently assumed solved.
- **The bridge (`iot/mqtt_bridge.py`) never inspects or stores any device's key** — it forwards whatever arrived in the MQTT payload's `"api_key"` field verbatim as an HTTP header, so a compromised bridge config exposes nothing devices haven't already published to the broker themselves.
- **`rotate_sensor_api_keys.py` only touches keyless sensors by default (idempotent, safe to re-run)** — it never silently rotates a key already in active use. `--force` exists for a deliberate full reissue (e.g. after a suspected leak of `iot/device_keys.json`), and is a manual, explicit choice, never automatic.

## What's real but incomplete (server-side region filtering for sensors and alerts, user-requested follow-up)

- **This closes the last remaining piece of a gap flagged since Phase 11: `GET /sensors` and `GET /alerts` previously had no `?region_id=` filter of their own** — the Authority dashboard scoped them client-side, against whichever villages the selected region's own (already region-scoped) `/villages` call returned. That worked correctly (verified against real cross-valley data when Chamoli's sensor fleet was provisioned), but left the actual region boundary enforced only in frontend code, not the API contract itself. Both endpoints now accept `?region_id=`, using the exact same real `Sensor`/`Alert` → `Village` → `MicroCatchment` → `Region` join `/villages`, `/catchments`, and `/risk/map` already use. Omitting the param keeps every caller written before this follow-up working unchanged — same "additive, never a behavior break" discipline used for every other `?region_id=` filter in this project.
- **A sensor with no village assigned (`village_id IS NULL`) never matches any `region_id` filter** — same as it never appeared in any region-scoped village list either. No seeded sensor is currently in this state, but the join is written to degrade the same honest way (silently excluded, not an error) if one ever is.
- **The frontend's own client-side scoping logic was removed, not just left in place alongside the new server-side filter** — `AuthorityView.tsx` now passes `selectedRegionId` straight through to `getSensors`/`getAlerts` and uses their results directly, rather than re-filtering a bigger unscoped list in JavaScript. This means the region boundary a user actually sees is now enforced by the same backend code path a non-browser API client would get too, not a frontend-only convenience.
- **A real, unrelated test-fixture bug was found and fixed while adding this follow-up's own tests**: two pre-existing failure-mode tests (`test_failure_modes.py`, Mode 5) posted sensor readings against the real seeded `esp32-kedarnath-rain-01` device, silently assuming it stays keyless forever. That assumption broke the moment the device-authentication follow-up's own live verification rotated a real key onto it in this same sandbox — a concrete demonstration of exactly the kind of test-fixture leakage this project tries to avoid. Fixed by giving those two tests their own dedicated, always-keyless throwaway sensor instead of depending on a real fleet device's current key-rotation state.
- **A second, genuinely unrelated bug was found live on the user's own machine while re-verifying the sensor pipeline for this follow-up**: `iot/simulate_sensor_publisher.py` called `client.connect()` and began publishing immediately, without waiting for the broker's actual `CONNACK` — a real race condition that could throw "the client is not currently connected" on the very first publish if the broker was even slightly slow to accept the connection. Fixed by waiting for the real `on_connect` callback (bounded to a 10-second timeout, so a genuinely unreachable broker still fails fast and honestly) before publishing anything, plus wrapping the initial `connect()` call itself in a try/except so an unreachable broker produces a clear log line instead of a raw traceback — matching the handling `iot/mqtt_bridge.py`'s own `on_connect`/`connect()` already had.

## What's real but incomplete (real-regional-data fallback for offline sensors, user-requested follow-up)

- **"Why do we need the simulator if we have real values" was the actual question that prompted this**: the IoT sensor network and the real Open-Meteo providers (`app/providers/base.py`, already used by the risk engine) were, until now, two completely disconnected data paths. No physical ESP32 hardware exists anywhere (see `docs/IoT_Architecture.md`), so with the simulator stopped, `GET /sensors` had nothing honest to show for an offline device except a bare dash. `_to_sensor_out` now falls back to a REAL Open-Meteo regional-weather estimate for a sensor's village whenever that sensor has no live/fresh reading — never fabricated, always tagged `fallback_source: "derived"` so it can never be confused with `last_value`/`last_reading_source` (that device's own actual observation).
- **A regional model estimate, not a hyperlocal ground-truth reading** — same honesty caveat `RealRainfallProvider`/`RealSoilMoistureProvider` already carry for the risk engine's own use of them: real, live, third-party data, but a general-purpose forecast/land-surface model's nowcast for the village's coordinates, not a calibrated instrument at that exact point.
- **Only rainfall and soil_moisture sensors get one.** Open-Meteo has no water-level or ground-tilt product at any resolution — a `water_level`/`tilt` sensor's `fallback_value` stays `null` honestly rather than the route guessing with an unrelated number.
- **`status` is never changed by this.** A sensor showing a fallback estimate still honestly reports `status: "offline"` or `"stale"` — the fallback is a UI convenience for the value cell only, never a claim that the device itself is reporting.
- **Cached per (sensor type, ~110m-rounded coordinate, calendar hour)** and fetched CONCURRENTLY across every unique village/type combo needed for one `GET /sensors` response (`_prefetch_regional_fallbacks`, `ThreadPoolExecutor`) — this exact N-sequential-real-calls anti-pattern was already found and fixed once for `GET /risk/map` (`prefetch_readings`, ~48s regression); this follow-up reused that fix rather than reintroducing the same bug in a new place. Caught live in this build sandbox: an early sequential version of this feature hung the test suite past 90s fetching all 12 seeded devices one at a time against a network-blocked host.
- **This exact HTTP call could not be executed inside the sandbox this code was built in** — same disclosed network restriction as `RealRainfallProvider`/`RealSoilMoistureProvider` themselves (see their docstrings and `docs/Data_Sources.md`); verifying it live needs the user's own machine, which does have real network access.

## Structural limitations that will remain true even once built

- **Limited historical event labels.** Himalayan flash-flood/landslide event records are sparse; the ML layer (Phase 5) will be explicit about sample size and will not claim validated operational accuracy without enough labelled events to support it.
- **The IoT pipeline is real; the hardware behind it isn't.** Phase 8's MQTT broker, bridge, and ingestion API are real code, actually run end-to-end (see `docs/IoT_Architecture.md`). No physical ESP32 boards exist in this build environment, so a simulator (`iot/simulate_sensor_publisher.py`) publishes on the MQTT side instead of real firmware — always declaring `source: simulated`, never presented as equivalent to a real reading in the UI.
- **Limited pilot geography** (5-10 villages in one valley) — the architecture is designed to extend to more districts/states later, but nothing here has been validated beyond the pilot.
- **Public-data resolution** (DEM grid size, satellite soil-moisture footprint) is coarser than a village-scale decision arguably needs; this is a known constraint of using public data sources rather than a bespoke sensor network.
- **Lead-time estimates are a prototype metric**, not an operationally-validated hydrological forecast — this will be labelled as such everywhere it's shown (problem-statement item 14).
- **This is a decision-support prototype for authorized personnel**, not an autonomous evacuation-ordering system, and not an official warning mechanism — this disclaimer appears in the API root response and will appear on every dashboard.

## What would be needed before real-world deployment

Field calibration against real sensor networks, operational validation of the risk model against a longer historical record, integration agreements with the actual data-owning agencies (IMD, ISRO/NRSC, CWC), a security/authentication implementation beyond the MVP interface, and sign-off from the disaster-management authorities who would actually act on its output.

## Wind overlay (map)

The optional "Show wind" layer on the Authority map draws animated particles from **real** Open-Meteo current 10 m wind, fetched on a coarse grid (default 7x7) over the villages' extent and cached for an hour per area. It is regional context only: the underlying model resolves roughly 2-11 km, so terrain-channelled winds inside narrow Himalayan valleys are **not** shown, and it must not be used to infer conditions at a specific village. It is not an input to the risk model. The grid is fetched by the viewer's own browser directly from Open-Meteo (free tier is rate-limited per IP, and shared hosting IPs such as Render's free tier get 429s), falling back to the backend's `GET /wind`. If both fail, the API returns 503 and the UI says wind is unavailable; nothing is simulated. Particle speed is a visual scale (colour encodes m/s bands), and `prefers-reduced-motion` gets a static streak frame instead of animation.
